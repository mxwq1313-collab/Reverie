# 窗口缩放渲染专项验收 · 2026-10-17

> 此文保留早期定位过程；当前 935 项回归、原生采集、WGC 录像及发布状态以 [2.3.0 验收记录](SIXU_2_3_0_READINESS.md) 为准。

## 范围和基线

权威源码为本仓库，基线提交 `c728f92`，应用版本保持 2.2.2。桌面应用使用 Python 3.10、Tkinter/ttk 8.6、Canvas、Pillow 和 PyInstaller；仓库附带的 Web 导出界面不是桌面窗口的渲染链。没有 React/Vue/Electron/Tauri，也没有桌面 DOM、ResizeObserver 或 CSS 动画。

本轮使用自建归档和生成内容，不读取真实微信、不发送模型请求。所有诊断日志、源码基线和本地构建放在 `build/ui_render_perf_20261017/`。

## 已定位的问题

1. `ResizeViewport.pin()` 固定旧工作区尺寸，根窗口 Configure 重置 120ms 计时；连续拖动时工作区被裁切或露出容器底色，停止后才集中排版。
2. `NativeResize` 和 `ResizePreview` 在重页面捕获窗口，`place_forget()` 隐藏真实分栏，然后反复缩放截图、分配 PhotoImage，最后切回真实控件。旧测试明确要求控件不可见，因此旧测试通过不能证明连续原生布局稳定。
3. 分栏布局用外层容器尺寸计算，但 PanedWindow 的原生尺寸稍后才更新，最大化/还原后可出现 AI 栏宽度漂移。人工验证复现后增加实际分栏 Configure 触发及回归。
4. `HoverHint.show()` 两次同步 `update_idletasks()` 会排空全应用的待处理布局，嵌套进入昂贵重绘。探索性聊天场景剖析记录过一次约 1.04s 的提示回调，改为异步定位。
5. 消息、转发与 Codex 对话使用反复重置的尾端计时，拖动期间正文不及时跟随。改为保留单个待处理布局，读取最新尺寸；保留可见区域虚拟化、文本测量缓存、媒体缓存与已有分批预算。

没有发现缩放时重新查询数据库、重载图片或重建全应用的调用链。Canvas 继续复用图元，媒体仍使用已有异步缩略图服务。现有字体、配色、图标、间距、圆角、阴影和页面功能保留。

## 修改

- `application_window.py`：合并根窗口/容器/分栏的布局请求，移除冻结与截图调用，布局键包含实际分栏宽度。
- `resize_viewport.py`：真实分栏持续映射，由 Tk geometry manager 连续填满容器。
- 删除 `native_resize.py`、`resize_preview.py`：移除窗口事件监听线程、捕获线程池、临时截图画布和切换路径。
- `browser_panel.py`、`copilot_shell.py`：使用实际尺寸，复用调度，跳过相同分隔位置。
- `message_widgets.py`、`forward_message.py`、`agent_panel.py`：合并连续文本布局，不等待拖动停止才刷新。
- `symbol_actions.py`：异步提示框定位，取消待处理任务后可安全关闭。
- 回归测试及 `resize_release_check.py`：验收原生控件持续可见、实际尺寸跟随、Unicode/选区/撤销与宽度保存。
- `tools/resize_probe.py`：可复现的合成窗口测量入口。

## 验证

基线 c728f92 与候选源码各做 3 轮交替测量，每轮 52 次尺寸请求；四类页面共 24 次独立进程运行。GUI 测量串行，没有同时运行其他测试或构建。计时包含持续缩放和其后 800ms 稳定期，使用 8ms 心跳和 cProfile；下表为各轮 p95 间隔的中位数。早期探索性测量、曾重叠运行的结果不作为最终对照。

| 场景 | 旧版 p95 心跳间隔 (ms) | 候选版 (ms) |
|---|---:|---:|
| 48,120 字符文字工具 | 72.885 | 169.506 |
| 100 条长消息 | 78.260 | 171.305 |
| 3 个展开转发 | 72.824 | 175.263 |
| 14 条 Markdown 对话 | 72.507 | 124.595 |

候选版的 12 轮测量中工作区隐藏次数均为 0、截图帧均为 0、Tk 回调异常均为 0，最终工作区尺寸与容器相同；文字工具和 Codex 测量的原文、控件及选区均保留。旧版文字工具每轮工作区隐藏 1 次、产生 51 张拉伸截图；其他场景主要依赖固定旧尺寸，实际工作量不同。

**性能结论：未达到连续缩放流畅度目标。** 取消冻结后恢复真实排版，p95 间隔在四类场景均更高。减少隐藏/恢复及布局错误是已验证的正确性改善，不能据此声称整体性能提升或零闪烁。候选源码剖析中大部分时间落在 Tk 原生 mainloop，包含正常消息等待、原生布局、绘制及系统合成等待，cProfile 不能把这些部分分开；Python 布局回调占比较低，仍需原生 CPU/GDI/消息时序采样解释，不能单凭此归因显卡驱动。

原生窗口实验只作用于独立合成测试进程：WS_CLIPCHILDREN/WS_CLIPSIBLINGS 已开启，重复设置 p95 176.845ms；分层绘制 p95 182.270ms、最长 296.832ms，没有明确收益；WS_EX_COMPOSITED 导致测试窗口长时间无进展，已精确停止本轮测试进程。上述实验设置全部未进入生产代码。微软的[扩展窗口样式说明](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles)及[双缓冲延迟说明](https://devblogs.microsoft.com/oldnewthing/20171018-00/?p=97245)用于核对 API 的适用条件；最终是否采用依据本机实测。

## 限制

下一步需要只针对合成窗口进程的原生 CPU/GDI/窗口消息时序采样，以及高帧率拖动录像。重点区分 Tk 8.6.12 原生绘制、Windows 消息泵与系统合成等待；评估其他 Tk 版本须单独分支和完整兼容验证，不在本轮直接替换运行时。


事件循环心跳间隔不等于真实显示帧率；窗口状态截图不能证明拖动过程每一帧都没有闪块。原生绘制耗时与应用内布局耗时分别报告。旧截图方案与真实重排的工作量不同，不把去掉截图后的控件稳定性改善自动解释为速度提升。
