# P0 C 显式副本迁移与读取兼容验收

日期：2026-10-14（Asia/Shanghai），基线af74332。验收为开发源码；应用版本保持0.8.0。默认归档继续Schema2；新增的Schema3只能通过明确的upgrade-copy操作创建到新目标。

## 已实现与兼容承诺

新增命令：

```powershell
python -m cli upgrade-copy "D:\archives\chat.db" "D:\archives\chat-v3.db"
```

仅接受已登记、没有SQLite日志/共享文件的本机Schema1/2归档。以SQLite只读连接和一致性备份创建独立临时副本，验证完整性后只在副本事务内迁移；逐表比较旧字段、ID、原文、来源、计数及摘要，检查外键和结构，最后原子创建一个不存在的新目标。原库仍可用旧版打开；旧版不能打开Schema3，新版可以读取旧库和升级副本。旧v1→v2默认备份迁移行为仍保留，不默认将v2升级到v3。

Schema3增加媒体/关联、来源、导入会话/批次和归档元信息基础表，扩展消息/会话约束，保留旧ID与autoincrement高水位、自定义索引及历史重复。消息和归档内容版本由登记触发器维护，删改后引用失效，修改后再还原原文也不会复活旧引用。触发器名称、实际定义、关键外键和元信息需符合登记结构。

已迁移的私聊文本可由旧CLI、桌面控制器/浏览、网页所用服务、Codex只读工具与HTML/TXT导出读取；新文本导入的来源映射在同一事务写入。旧文本读取接口明确限定text且有接收者，不把群聊/非文本记录冒充私聊；可读导出遇到范围内未支持类型明确拒绝。本阶段是存储和兼容基础，不代表已完成媒体/群聊解析、展示或导出。

## 保护与失败行为

- 同路径、既有目标、目标竞态创建均拒绝，不覆盖；最终使用同一文件系统的create-if-absent硬链接交付。文件系统不支持安全创建时失败，保留原文件。
- 先独立检查备份、原库应用标识/Schema/外键/完整性及空间；源变化、WAL/SHM/journal、未知触发器/视图、坏时间或未知版本拒绝。
- 表重建只在临时副本进行，外键在事务外关闭、事务内执行正确的新表→复制→删除旧表→命名流程，之后检查并恢复；没有修改原库。
- DDL后故障或摘要不一致会回滚并只清理本操作独占临时目录；新目标不出现，外部竞态创建的文件保留。
- 原库字节SHA-256与文件身份/时间在交付前复核。Schema1→2沿用既有UTC规范化，保留原时间点，其他原字段逐项保持。

实现依据为[SQLite表重建流程](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes)与[SQLite备份API](https://www.sqlite.org/backup.html)；本文的文件保护、模式约束和验收是本项目实现，不外推第三方性能。

## 开源差距和下一方向

[WechatExporter](https://github.com/BlueMatthew/WechatExporter)在多类型、群名称及离线导出方面已有资料和代码；本项目现在有显式迁移和类型基础，但获取、渲染、媒体生命周期和增量闭环尚有差距。不能把建表成功当成达到其产品能力，不能用测试项数量宣称更强。

下一P0-D先在固定SDK和独立消息快照上验证跨分片稳定排序/游标、超过100000项的有界读取与批次事务/恢复；SDK公开完整历史宣传不代替本机证据，未知二进制文本继续保留隔离。导入会话/批次状态由同一权威SQLite事务维护，不能用独立日志冒充提交状态。之后P1优先把Codex的连接/登录/会话/引用状态及升级副本入口做成清楚的使用流程，再扩展检索、群聊与附件。
